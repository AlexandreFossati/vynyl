## How to work each task

1. Create the change in OpenSpec (`/opsx:propose`) using the task's "Change description" as a starting point.
2. The agent implements **only** the task's scope (`/opsx:apply`) and really verifies (lint, typecheck, tests, execution), checking the checkboxes as it goes.
3. The agent delivers the final report (format defined in `CLAUDE.md`) and a suggested commit message. **It does not commit.**
4. The user reviews the diff and commits; only then is the task's checkbox checked in the Overall status. After that, archive the change (`/opsx:archive`).
5. If the review changes any pattern or decision, update `PROJECT_GUIDE.md` and the **Approved patterns** section before the next task.
6. Write down 3–5 lines for `AI.md` (what worked well/badly in this task). It is easier now than reconstructing it at the end.

**Why this order**: T1 fixes the skeleton and the database. T2 and T5 are **model tasks**: a complete vertical slice on the backend and another on the frontend, so you can review and adjust the pattern *before* replicating it (T3 and T6), which avoids rework at scale. T4 comes after the CRUD because singleflight applies to the reads that already exist. T7 integrates everything and only makes sense with the API and SPA ready. Backend before frontend because the SPA consumes the real API; T5 only needs the T2 endpoint.

**Decision on the "first endpoint"**: I recommend `GET /api/products` (list with pagination and search). It forces the whole foundation to exist (app factory, config, logger, database, seed, query validation, mapper, response envelope, error handler) and is the basis of the dashboard. The trade-off is that the **write** pattern (body validation, 201/`Location`, 409) is only evaluated in T3. If you prefer to evaluate writes first, switch to `POST /api/products`.

## Approved patterns

> Fill in **after the T2 review** (backend) and **after the T5 one** (frontend). Agents of the following tasks must treat this section as mandatory. While it is empty, sections 4 and 10 of the guide apply.

### API (approved in the T2 review)
- File/function naming convention per layer: files in `kebab-case` with the layer suffix, in top-level folders (`products.repository.ts`, `.service.ts`, `.handler.ts`, `.routes.ts`, `.mapper.ts`). Each layer is a factory function `createXxx(deps)` that returns an exported interface (`ProductsRepository`, `ProductsService`, `ProductsHandler`). `*.test.ts` tests next to the code; test helpers in `src/test/`. New resource = one file per layer, following the same pattern.
- How dependencies are injected: by parameter, in an object (`{ productsRepository }`), with no module singletons. Only `server.ts` (composition root) reads the environment and creates real resources; `createApp({ db, logger })` composes repository → service → handler → router.
- Validation pattern (where and how): `validate({ query, params, body })` middleware on the route, with Zod schemas from `@vynyl/shared` (`strictObject`: unknown key or repeated parameter → 400). The result stays in `res.locals.validated` and is read with `getValidated<T>(res, source)`; never rewrite `req.query` (read-only in Express 5). Errors become `details: [{ path, message }]`.
- Domain error → HTTP response pattern: throw `AppError(code, message, { details, cause })`; the status comes from the exhaustive `STATUS_BY_CODE` map. The central `error-handler` is the only point that responds with errors (envelope `{ error: { code, message, details? } }`); 5xx and unexpected errors respond with a generic `INTERNAL_ERROR` and are fully logged with `req.log.error`. Async handlers need no `try/catch` (Express 5). Route with no match → `NOT_FOUND`.
- Logging pattern: `pino` via `createLogger`; one log per request (`pino-http`) with `X-Request-Id` (reuses `[A-Za-z0-9_-]{1,64}`, otherwise UUID) and level by status (info/warn/error). Serializers on an **allowlist** (id, method, URL, status): never headers or bodies. No `console.*`.
- Test style (unit, repository, route): observable behavior, without mocking what is under test. Repository, seed and routes use a real `:memory:` database (`createTestDatabase`); routes via Supertest over `createApp` (`createTestApp`); fakes only for the layer below (service with a fake repository, handler with a fake service); logs captured with `createLogCapture`; counts derived from the data set; `vi.waitFor` instead of fixed waits; cleanup of temporary files tolerant to failure (Windows).
- Adjustments requested in the review: none; patterns approved as implemented. Decisions added during implementation: parameters prefixed with `_` may go unused (ESLint rule, required by Express's `_next`); optional `.env` at the root (the environment takes precedence); paths derived from the code's location (`getPaths`) and a relative `DATABASE_PATH` resolved from the repository root; an empty data set is rejected in the seed; on Windows libsql keeps the database file open after `close()` (the T7 e2e only deletes the file after the process ends).

### Frontend (approved in the T5 review)
- Component convention per level (Atomic Design): one component per `PascalCase.svelte` file in `components/{atoms,molecules,organisms,templates,pages}`, with the `PascalCase.test.ts` test next to it. Typed props with `$props()`; events as *callback props* (`onclick`, `onsearch`, `onpagechange`), no `createEventDispatcher`; content via *snippets* (`children`). Atoms forward the remaining props to the native element (`...rest`). Only what a screen uses gets in. Dependencies only go down; no component below `pages` imports `lib/api` (enforced by `no-restricted-imports` in `eslint.config.js`).
- Data access pattern in pages: the page receives the API via a prop, with the real one as the default (`{ api = productsApi }: Props`), which allows testing it with a fake API without mocking modules. `lib/api` has `http-client.ts` (`request` with timeout, cancellation, retry only on idempotent methods, backoff with full jitter, `Retry-After`, typed `ApiError`) and one module per resource that validates the response with the schema from `@vynyl/shared`. Each new query cancels the previous one with `AbortController` (a `load()` function called by an `$effect` whose *cleanup* aborts) and the response of a cancelled request is ignored. Routing: `lib/router.svelte.ts` (History API, `router.path` and `router.navigate`); the page is chosen in `App.svelte`. No state or fetching library.
- States pattern (loading/empty/error): the `StatusMessage` molecule (title, message, `busy`, action) serves all three. Loading (first load) = `busy`, `status` role; empty = `status` role with a "Clear search" action when there is a search; error = `danger` tone, `alert` role, no technical details, with "Try again" that repeats the same query and restarts from the loading state. Reloads after the first keep the previous list with `aria-busy`.
- Approved tokens and visual guidelines: `styles/tokens.css` is the single source of colors, spacing (4/8/12/16/24/32/48), typography, radii, shadows, `--tap-size` (44px) and the focus ring; components use only `var(--...)` (no literal colors). Scoped styles in each component's `<style>`, mobile-first with `min-width` at 640px and 1024px (literals, since variables do not work in `@media`). System font, global visible focus in `base.css`, `.visually-hidden` for screen-reader-only text. A test verifies the WCAG contrast of the token pairs (4.5:1 text, 3:1 focus).
